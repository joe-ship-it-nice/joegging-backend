The starting line

Built on Joefriends.

Joegging reuses and extends the Joefriends Express backend. Existing account, post, profile, and friendship features provide the foundation. Supabase supplies authentication, database storage, and image storage; the Express API continues to manage application data.

Frontend

React, Vite, and React Router provide the login, signup, feed, friends, and profile pages.

Backend

The existing Express API validates requests, checks authentication tokens, and reads or writes application data.

Supabase

Authentication manages sessions, PostgreSQL stores community data, and Storage holds running photos.

The development journey

Checkpoint walkthrough.

This report follows the requirements shared for the project. The foundation section summarises the initial full-stack work; cover testing and deployment, Google OAuth, and image posts.

Foundation · Full-stack integration

Turn Joefriends into a running club.

  1. Reuse the Joefriends API. Copy the existing project into the Joegging workspace, preserving its post and friendship functionality.
  2. Connect frontend and backend. Use API endpoints for posts, users, friendships, and profile data. Configure the frontend API address through VITE_API_URL.
  3. Manage sessions with Supabase. Keep the React authentication context in sync with session changes and attach access tokens to protected API requests.
  4. Protect application pages. Wait for session initialisation before redirecting guests away from the feed, friends, and profile pages.
  5. Redesign the experience. Replace Joefriends branding with Joegging, introduce running prompts, and replace DitherVeil with a running-video background.

The backend remains an extension of the Mission 9 submission. Deploying it to a separate Joegging project does not replace it with a different API.

Checkpoint 2 · Testing and deployment

Test the journey before shipping.

  1. Establish separate repositories. Point the frontend and backend Git remotes to their respective Joegging repositories, preserving the earlier project history.
  2. Create the testing branch. Develop browser tests on feature/add-automated-tests.
  3. Add Playwright tests. Test email/password login, session persistence after a refresh, and creating a post that remains visible after refreshing.
  4. Configure the test environment. Keep test credentials in an ignored local environment file. Configure Playwright to start both the frontend and backend.
  5. Automate checks with GitHub Actions. Download both repositories, install dependencies, run lint and the production build, install Chromium, and run the tests. The frontend workflow runs on pushes and pull requests.
  6. Review and merge. Open a pull request, review the changes with AI assistance, record the findings, and merge after successful checks.
  7. Deploy both applications. Deploy the Express backend and Vite frontend as separate Vercel projects. Configure their Supabase environment variables.
  8. Support direct page visits. Add a frontend vercel.json rewrite through feature/configure-deployment so routes such as /feed and /login work on refresh.
  9. Verify frontend automatic deployment. Confirm that merging the OAuth improvements into main produces a working production update.

Verified: local lint, build, and two browser tests passed. A GitHub Actions run also passed. Frontend automatic deployment was confirmed. A deployment triggered by a new backend commit still needs explicit verification.

Checkpoint 3 · Google OAuth

Join the club with Google.

  1. Configure the Google OAuth client. Connect Google's client credentials to the Supabase Google provider and use Supabase's callback URL for Google's redirect.
  2. Add Google login. Call signInWithOAuth with the Google provider from the frontend authentication context.
  3. Restore the session after returning. Subscribe to authentication state changes and let the route guards send signed-in users to the feed.
  4. Connect the user profile. Retrieve profile data from the protected GET /profile route using the authenticated user's identity.
  5. Allow the production return URL. Add https://joegging-frontend.vercel.app/login to Supabase's allowed redirects.
  6. Review and improve the implementation. On feature/add-google-oauth, clear old login errors when retrying, reuse the authenticated API helper in Profile, ignore aborted responses, and handle missing dates.
  7. Validate and merge. Run lint, build, and existing browser tests; manually verify Google login and profile behaviour; review and merge the PR. Confirm the updated profile works on the live website.

Google login and Profile were manually verified on the deployed app. The existing automated tests cover email/password login and posting, not Google's external sign-in screen.

Checkpoint 4 · Image posts

Share the run, not just the words.

  1. Use Supabase Storage. Upload running photos to the running-photos bucket using a user-specific folder and a unique filename.
  2. Validate the selection. Accept non-empty JPG, PNG, or WebP files up to 5 MB in the frontend. Display upload progress and disable repeated submissions.
  3. Associate the image with a post. Send image_path to the existing POST /posts route. The backend checks the path belongs to the authenticated user's folder and checks access.
  4. Store the image reference. Save the image path and a stable authenticated URL with the post. Generate temporary signed image URLs when reading the feed.
  5. Display the photo. Render the returned image URL beside the post content, author, visibility, and creation date.
  6. Handle loading failures. On the frontend branch feature/add-image-posts, add a reusable PostPhoto component that shows a helpful message when an image fails to load.
  7. Test the behaviour. Verify uploading a photo, viewing it after refreshing, and displaying the fallback using a deliberately invalid image URL. Restore the real URL after the test.

Upload, refresh, and fallback behaviour were reported working. The final image-post PR merge and production deployment should be confirmed before marking this checkpoint fully complete. Friends-only photo access also depends on the database and Storage policies, not just the frontend controls.

The API behind the club

Existing routes, extended.

Method Route Purpose
POST /signup Create an email/password account.
POST /login Retained Mission 9 login endpoint; the current frontend signs in through Supabase directly.
GET /profile Return the authenticated runner's profile.
GET /posts Return visible posts with temporary photo links.
POST /posts Create a post with an optional uploaded-photo reference.
GET /users List other users.
GET / POST /friends List friendships or send a friend request.
PATCH /friends/:id/accept Accept a pending request addressed to the current user.

Lessons from the run

Problems solved along the way.

Google login returned to the login page

Session handling moved into the Supabase authentication context. Protected routes wait for authentication initialisation, and production redirect URLs were configured for the deployed frontend.

Playwright could not start the backend

Port 3000 was already occupied by a development server. Stopping the manually started servers allowed Playwright to manage both servers itself.

Git showed generated files and dependencies

Updating .gitignore excluded node_modules, dist, environment files, and Playwright output. The staged file list was checked before commits.

Feature work started before branching

OAuth and uploads were initially implemented before the requested feature branches. Later branches contain genuine review improvements and fixes.

Remaining improvements

Automated post tests leave test records behind. Failed post saves can also leave unused uploaded files. Future work should introduce safe cleanup, add image-upload browser tests, verify Storage policies, and review dependency audit findings.
